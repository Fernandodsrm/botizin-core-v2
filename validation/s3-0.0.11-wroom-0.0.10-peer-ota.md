# S3 updates controlled from the WROOM OLED

The WROOM gains a sixth menu area, Atualizacao S3. Five visible rows scroll while the approved yellow title/button instructions and blue content remain unchanged. SDA21/SCL22 and OK25/UP27/BACK32/DOWN33 are preserved. The S3 retains its display-free firmware, Wi-Fi settings, partition geometry and device-only ThingsBoard credential. Both boards keep automatic manifest checks enabled every 60 seconds.

## Manual flow

The S3 implements the WROOM's existing five-minute manual hold, exact candidate/version/SHA/current-boot binding and wrap-safe expiry. Checking never writes firmware. First OK opens confirmation; second OK submits the exact displayed candidate. Back declines without installing. Cancellation gives five minutes before automatic OTA resumes. Each board downloads only its own board-specific HTTPS manifest/image and verifies SHA from received data and flash before reboot.

The WROOM sends one mutation per explicit action and never retries a timed-out confirmation automatically. It polls authenticated status while viewing OTA S3 or monitoring a requested installation. A lost ACK displays uncertainty, not success. Final version confirmation requires a different S3 boot, the requested version, VALID OTA state and matching running/boot partition. The monitor expires after five minutes; it reports failure or lack of proof instead of spinning forever. Confirmation freshness is at most 15 seconds and remote candidate expiry is reduced by round-trip duration plus one second.

## Local protocol and pairing

Both boards receive the same random 32-byte key via authenticated ThingsBoard peer_pair RPC, with existing issued_at_ms/command_id freshness checks. The key is stored in a separate botizin-peer NVS namespace, never returned in telemetry, never printed and never embedded in public source or release metadata. This RPC changes pairing configuration only; it does not install firmware or change Wi-Fi.

S3 GET /peer/challenge returns a one-use nonce expiring after ten seconds. POST /peer/ota accepts status/check/confirm/cancel only, with JSON bodies <=1024 bytes. HMAC-SHA256 binds request direction, nonce and exact body. Responses bind response direction, nonce and exact JSON; the WROOM verifies the MAC, board, origin and command ID before using a reply. Invalid authentication does not enqueue work. The control transport is HTTP on the existing home LAN; HMAC authenticates commands/replies but does not encrypt status data. The key itself travels through the authenticated HTTPS cloud RPC only.

The IP remains the existing 192.168.0.36. IP discovery and use without the home router are future work.

## Progress and limits

The S3 services bounded local status requests inside its existing download loop, and rejects competing local uploads/reboots during Internet OTA. Bytes and percentages come from the S3's actual write counters. TLS handshakes, manifest requests and SHA verification are still synchronous; during these phases the screen may temporarily await a reply. No continuous progress is fabricated. Button presses are preserved during ordinary status polls, while presses during explicit network mutations are discarded to prevent a delayed OK becoming a confirmation.

## Verification

- Existing peer status parser tests pass.
- Existing exact candidate/version/SHA/boot, expiry and timer wraparound tests pass for both boards.
- Expanded navigation tests pass for the sixth menu area, S3 query, unavailable install, first/second OK, decline, expiration, cancellation, wrapping and queued-action guard.
- Actual shared peer_auth.h passed a host HMAC known-vector test using an OpenSSL-backed mbedTLS adapter, including nonce/body/direction mismatch, malformed keys and idempotent NVS persistence.
- Existing cloud PING, manual OTA widget and server-clock tests pass after accepting WROOM 0.0.10. S3 PING accepts 0.0.10 and 0.0.11.
- Build/release records below identify the exact compiled source, image size and SHA. Physical OLED and an S3 installation started from WROOM still require user observation; publication alone does not prove them.

The user has already confirmed the WROOM's manual installation path. No additional test-only WROOM release is required for that earlier milestone.
