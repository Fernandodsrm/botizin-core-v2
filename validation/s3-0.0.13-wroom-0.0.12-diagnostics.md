## Sampling and limits

Memory sampled on the existing loop every 5 seconds; no new tasks, NVS writes, ring log or dedicated network request. Fixed counters track operation duration, calls and supported failure outcomes. Existing cloud upload includes a bounded diagnostic summary once per existing send cycle. OLED refreshes at most once per second from cached data. S3 status uses existing bounded read-only fetch every 10 seconds only while its diagnostic/connection information is visible; other times 30 seconds.
RAM figures distinguish internal free/minimum/largest block and external PSRAM free. Firmware spare capacity is current application size compared with the unchanged next OTA slot. Loop maximum gap includes intentional synchronous network waits and OTA and is NOT CPU utilization. All maxima/minima are since this boot. Values are not capacity promises or automatic safety thresholds.

## Deliberate scope

No LED GPIO changes, radio/Bluetooth activation, Wi-Fi reconfiguration, pairing key changes, reset RPC or partition changes. Controls honestly shows LED unavailable. Network blocking is measured, not silently solved by longer timeouts. Authenticated S3 OTA candidate/hash/boot/expiry binding and separate second confirmation stay in place. Public /status diagnostics are read-only local reports; OTA commands still require HMAC. Remote values carry report age and become explicitly old after the existing contact threshold.

## Device observations and sampler correction

Both first diagnostic releases actually booted VALID with automatic enabled and pairing retained. WROOM 0.0.11 boot 667e03a0be81925a, S3 0.0.12 boot 8c0fa0eecd27bfcf. WROOM observed internal free 160068/minimum 98012/largest block 110580 bytes; loop maximum gap 2731020 us, cloud RPC maximum 2698623 us, OLED maximum 29417 us. S3 observed internal free 259552/minimum 204532/largest block 167924 bytes, external RAM free 8374680 bytes. These are observations, not guarantees of simultaneous future modules.

Sampler maxima were unexpectedly 244682 us WROOM and 93357 us S3. Inspection of Arduino ESP32 core 3.3.12 cores/esp32/Esp.cpp confirmed getSketchSize invokes esp_image_verify every call. Initial diagnostic implementation called it every 5 seconds: this was an avoidable performance mistake. Follow-up WROOM 0.0.12 / S3 0.0.13 compute the firmware margin exactly once before the first boot status and measure that startup cost separately as diag_flash_init_us. Periodic memory samples never scan the firmware. A host test with a simulated 250 ms flash verification proves repeated and wraparound-period sampling does not repeat the scan. Actual corrected sampling cost remains subject to post-boot verification.

## Corrected device verification

Cloud telemetry confirms WROOM 0.0.12 boot 63f2931b64accf03 and S3 0.0.13 boot 11a09c76e589d795; both VALID, paired, automatic enabled. WROOM periodic sampler maximum 196 us (17 samples at uptime 87s), S3 101 us (5 samples at uptime 26s). Flash verification cost is now separately recorded once at boot: WROOM 242585 us, S3 91776 us. Thus the recurring 244ms/93ms scans are removed and observed periodic memory collection is below 0.2ms on each board. This is measured sampling cost, not complete telemetry-send cost or CPU utilization. Cloud send/RPC and LAN waits remain separately measured.

WROOM static globals are 65984 bytes, 280 more than previous 0.0.10; binary grows 5344 bytes and leaves 62560 bytes in the preserved OTA slot. Physical menu acceptance is pending Fernando's observation. LAN S3 status had HTTP_-1/HTTP_-11 failures during the update sequence; no claim is made that network scheduling and local link stability have been solved by this release.
